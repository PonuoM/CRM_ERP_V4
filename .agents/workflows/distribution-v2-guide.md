# 📦 Distribution V2 (Smart Allocation Architecture)

ระบบแจกงาน Distribution V2 คือ **"ศูนย์กลางการกระจายลูกค้าระดับสูง"** ที่ใช้สำหรับนำรายชื่อลูกค้าจากถังต่างๆ (Baskets) มาแจกจ่ายให้กับพนักงาน Telesale แต่ละคน โดยมาพร้อมกับ **สถาปัตยกรรม Component-Based แบบใหม่ล่าสุด** และ **ระบบสมองกลป้องกันรายชื่อซ้ำซ้อน (Smart Allocation)**

---

## 🏗️ 1. สถาปัตยกรรมระบบ (System Architecture)

เพื่อลดปัญหา Code Monolith (ไฟล์เดียว 3,500 บรรทัด) ระบบ Distribution ปัจจุบันถูกเขียนด้วยหลักการ **Separation of Concerns** โดยแบ่งเป็นส่วนๆ ดังนี้:

### 📂 ไฟล์หลัก (The Orchestrator)
- **`pages/CustomerDistributionV2.tsx`**: ทำหน้าที่เป็นคอนเทนเนอร์หลัก (Container) เก็บเฉพาะ State ที่ใช้ร่วมกันระดับบนสุด และควบคุมการทำงานภาพรวม (เหลือเพียง ~700 บรรทัด)

### 🧩 Component ย่อย (The Modules)
แยกการทำงานตามหน้าต่าง (UI Sections) ไปไว้ที่ `components/DistributionV2/`:
1. **`DistributionFilterForm.tsx`**: จัดการเรื่องการค้นหาและฟิลเตอร์ลูกค้า (วันเวลา, แท็ก, สินค้า, ฯลฯ)
2. **`DistributionTelesaleTable.tsx`**: จัดการตารางรายชื่อพนักงาน, การแสดงผล **"เวลาทำงาน (Working Hours)"** ของพนักงานในวันปัจจุบันแบบ Real-time (ดึงจาก `user_daily_attendance`), การเช็คเวลาโทร (เลือกวันที่และกรองด้วยกะเวลาโทรได้ เช่น กะปกติ 09:00-18:00 หรือ กะวันเสาร์ 09:00-16:30), ระบบเลือกตัวพนักงานและกรองด้วย Supervisor
3. **`DistributionTargetSection.tsx`**: จัดการหน้าต่างตั้งค่าการแจกงาน (เป้าหมาย, เลือกโหมด Equal/Load Balance/Performance)
4. **`DistributionPreviewModal.tsx`**: แสดง Modal ตัวอย่างลูกค้าที่จะถูกแจกและคำเตือนเรื่องรายชื่อซ้ำซ้อน

## 🧠 2. ลำดับการแจก และกลไกกันรายชื่อซ้ำ (Lead Priority + Smart Allocation)

> ⚠️ **ปรับใหญ่ 25 ส.ค. 2026** — ก่อนหน้านี้หน้าเว็บจะ **เรียง pool ใหม่** แบบ Most-Constrained-First
> (ลูกค้าที่ผ่านมือพนักงานที่เลือกมาแล้วหลายคน ถูกดันขึ้นหัวแถว) และ Smart Allocation **ปิดไว้เป็นค่าเริ่มต้น**
> ผลรวมของสองอย่างนี้ทำให้ระบบหยิบ *รายชื่อที่เพิ่งหลุดจากมือพนักงาน (= เพิ่งถูกโทร)* มาแจกก่อน
> แล้วส่งกลับไปหาคนเดิม วัดจากข้อมูลจริง 10 วันย้อนหลัง: **~90% ของรอบแจก เป็นการแจกคืนคนเดิม 100%**
> ทั้งที่ค่าฐานในถังอยู่แค่ 6% ทีม CRM จึงแจ้งว่า "ได้รายชื่อที่เพิ่งโทรไป แจกแล้วไม่เกิดผล"

### 📊 ลำดับความสำคัญของรายชื่อ (จัดที่ SQL — `handleBasketCustomers`)
Backend เป็นผู้จัดลำดับทั้งหมด และ **หน้าเว็บห้ามเรียงใหม่เด็ดขาด**:

| ลำดับ | กลุ่ม | นิยาม | เรียงภายในกลุ่มด้วย |
|---|---|---|---|
| 1 | **A1** | ไม่เคยกดโทรเลย (ไม่มีแถวใน `call_history`) | ยอดขายปีนี้มาก→น้อย, ตกไปใช้ยอดสะสมถ้าทั้งถังเป็น 0 |
| 2 | **B** | เคยโทรติด และพ้น cooldown แล้ว | โทรติดล่าสุด **เก่าสุดก่อน** |
| 3 | **A2** | กดโทรแล้วแต่ไม่เคยติดสักครั้ง | พยายามโทรล่าสุด เก่าสุดก่อน |
| 4 | **cooldown** | เพิ่งโทรติดภายใน N วัน | ท้ายสุดเสมอ — แจกได้แต่ต้องกดยืนยัน |

- **"โทรติด"** = `call_history.status IN ('รับสาย','ได้คุย')` — ไม่นับ `ตัดสายทิ้ง`
  (ห้ามใช้ `call_history.duration` เด็ดขาด 99% เป็น 0)
- อ่านผ่านคอลัมน์แคช `customers.last_call_date` / `customers.last_talk_at` (migration 087)
  ไม่ใช่ GROUP BY สดจาก `call_history` 613k แถว
- **ยอดขายปีนี้** = `SUM(orders.total_amount)` ปีปัจจุบัน ตัด `Cancelled`/`Returned` ออก
  (ไม่ใช้ปีก่อน เพราะข้อมูล 2025 มีบิลซ้ำราว 14%)
  ถังเก่าอย่าง "1-3 ปี" ทุกคนจะได้ 0 โดยธรรมชาติ จึงตกไปใช้ `customers.total_purchases` อัตโนมัติ
- ลำดับกลุ่มปรับได้รายถังผ่าน `basket_config.lead_group_order` (ค่าเริ่มต้น `A1,B,A2`)

### ⏳ Cooldown แบบไฮบริด (`basket_config.cooldown_days`, ค่าเริ่มต้น 30 วัน)
ไม่ตัดรายชื่อที่เพิ่งโทรทิ้งจาก pool แต่ดันไปท้ายคิว และ:
- การ์ดถังแสดง `พร้อมแจก X · เพิ่งโทรติดใน N วัน Y ราย (อยู่ท้ายคิว)`
- ถ้าจำนวนที่ตั้งไว้ > จำนวนที่พร้อม → เด้ง popup บอกว่าจะต้องควักของที่เพิ่งโทรมาอีกกี่ราย
  (พร้อมบอกว่ารายที่ใกล้สุดโทรไปกี่วันที่แล้ว) ต้องกดยืนยันก่อนถึงจะไปต่อ
- จำนวนที่ฝ่าไฟแดงถูกบันทึกใน `distribution_sessions.cooldown_override_count` ตรวจย้อนหลังได้

### 🔒 Smart Allocation — เปิดถาวร ไม่มีสวิตช์ปิดแล้ว
- ตาราง `customer_assign_check` จำว่า "ลูกค้า X เคยถูกแจกให้พนักงาน Y"
- ตอนจับคู่ ระบบเดินไล่ pool **ตามลำดับที่ backend จัดมา** แล้วเลือกพนักงานที่ (ก) ยังมีโควตาเหลือ
  (ข) ไม่เคยถือรายนี้ (ค) ได้รับน้อยที่สุดในรอบนี้
- **หาคนรับไม่ได้ → ข้ามไปรายถัดไป** ไม่ยัดให้คนเดิม
  (ของเดิมมี Pass 2 ที่ยัดให้เพื่อเติมโควตาให้ครบ ทำให้พรีวิวโชว์เต็ม แต่ backend reject ทิ้งทีหลัง
  = แจกจริงได้ไม่ครบโดยไม่มีใครรู้)
- ถ้าแจกไม่ครบโควตา จะขึ้นคำเตือนพร้อมบอกว่าข้ามไปกี่รายเพราะติดเงื่อนไขซ้ำ
- ปุ่ม "แจกเพิ่ม" ใช้กติกาเดียวกัน (ดึงรายชื่อถัดไปตามลำดับ + เช็คซ้ำก่อนจับคู่)

### 🛡️ ความถูกต้องของข้อมูลตอนแจก (migration 089)
- **กันแจกทับเจ้าของเดิม** — ตอนแจกจะ `SELECT ... FOR UPDATE` ล็อกแถวลูกค้าไว้ แล้วเช็คว่ายังไม่มีเจ้าของจริง
  รายที่มีคนถือไปแล้วระหว่างทางจะถูกข้าม และส่งกลับมาใน `already_assigned_ids`
  (เดิมไม่มี guard นี้ เคยแจกทับเจ้าของเดิม 279 รายใน session #202 เมื่อ 16 ก.ค. 2026)
- **`customer_assign_check` มี UNIQUE KEY `(customer_id, user_id)` แล้ว** และ logic รีเซ็ตรอบเปลี่ยนจาก
  `COUNT(*)` เป็น `COUNT(DISTINCT user_id)` + จำกัดตาม `company_id`
  (เดิมนับ "แถว" ทำให้แถวซ้ำ 22,680 แถวดันยอดจนรีเซ็ตก่อนกำหนด — company 7 กระทบ 3,174 ราย)
- **undo คืน `basket_entered_date`** ด้วยแล้ว ผ่านคอลัมน์ `distribution_session_details.previous_basket_entered_date`
  (เดิมรายชื่อที่ดึงกลับจะกลายเป็น "เพิ่งเข้าถัง" แล้วไปต่อท้ายคิว)
- **กรอง `is_blocked` ต้องใช้ `COALESCE(is_blocked, 0) = 0`** เพราะมีลูกค้า 54,741 รายที่ค่าเป็น `NULL`
  (ในถังแจก 4,496 ราย) ถ้าเขียน `is_blocked = 0` เฉย ๆ คนกลุ่มนี้จะหายจากการแจกทั้งหมด
- **เกณฑ์นาทีโทร** — หน้าเว็บส่ง `call_filter_window` (วันที่+ช่วงเวลาที่จอใช้คำนวณ) ไปด้วย
  backend ตรวจซ้ำด้วยหน้าต่างเวลาเดียวกัน ไม่ใช่กติกาของตัวเอง และค่าเริ่มต้นวันที่บนจอ
  เปลี่ยนเป็น "วันทำการก่อนหน้า" (ข้ามเสาร์-อาทิตย์) — เดิมใช้ "เมื่อวาน" เฉย ๆ ทำให้ทุกวันจันทร์
  จอดึงยอดวันอาทิตย์ = 0 นาทีทุกคน กดปุ่มเลือกพนักงานตามเกณฑ์แล้วไม่ได้ใครเลย

## ⚙️ 3. โหมดการแจกงาน (Distribution Modes)

1. **แบ่งตามประสิทธิภาพ (Performance):** แจกให้ตาม % นาทีการโทร (Call Minutes) ใครโทรเยอะได้เยอะ
2. **แบ่งเท่ากันอัจฉริยะ (Smart Equal):** หารจำนวนแจกเท่าๆ กันทุกคน แต่จะแทรกแซงด้วย Smart Allocation เพื่อไม่ให้แจกรายชื่อที่เคยซ้ำ
3. **ปรับสมดุล (Load Balance):** มองจำนวนลูกค้าทั้งหมดที่ถืออยู่ ใครถือน้อยสุดจะได้เติมให้เต็มก่อน
4. **กำหนดเอง (Manual Quota):** กรอกตัวเลขเป้าหมายด้วยมือเป็นรายบุคคล

## ⚡ 4. การบริหารจัดการรายชื่อแบบกลุ่ม (Bulk Actions)

สำหรับหัวหน้าทีมที่ต้องการย้ายหรือดึงคืนลูกค้าจำนวนมากๆ ในคลิกเดียว:

- **⚡ ดึงคืนเข้าถังกลาง / โอนให้พนักงานอื่น (Transfer):** ดำเนินการย้ายรายชื่อของพนักงานทุกคนในบริษัทพร้อมกันเข้าถังกลาง หรือโอนให้ Telesale คนอื่นที่เลือก
- **ระบบคัดกรองเงื่อนไข (Transfer/Reclaim Filtering):** เลือกดึง/โอนได้ตามพฤติกรรมการติดต่อลูกค้า:
  - **ทั้งหมด:** ดึง/โอนลูกค้าในถังที่เลือกแบบเหมา
  - **ไม่มีการโทร:** ไม่รับสาย หรือยังไม่เคยโทรเลย
  - **โทรแล้วไม่นัด:** โทรคุยแล้วแต่ยังไม่สามารถปิดการขายหรือนัดหมายได้
  - **โทรและนัด:** ลูกค้าที่มี Potential มีประวัติการนัดหมาย
- **กำหนดถังปลายทางได้ (Destination Selection):** เมื่อเลือกกระทำแบบ "ดึงคืนเข้าถังกลาง" สามารถกำหนดจุดหมายปลายทางได้ 2 รูปแบบ:
  - **ตามถังอัตโนมัติ (Linked Pool):** [ค่าเริ่มต้น] ระบบจะส่งรายชื่อกลับเข้าสู่ถังกลางที่ตั้งค่าผูกไว้ (Linked Basket) ตามระบบนิเวศเดิม
  - **บังคับถัง (Force Basket):** สามารถเจาะจงบังคับรายชื่อทั้งหมดให้ไปรวมกันที่ถังใดถังหนึ่งที่กำหนดไว้ได้ทันที (เช่น "ถังพักรอแจก") โดยไม่ต้องสนว่าถังตั้งต้นจะผูกกับอะไรไว้
- **Strict Validation (ป้องกันการผิดพลาด):** ระบบบังคับใช้การตรวจสอบ `linked_basket_key` อย่างเคร่งครัด หากแอดมินลืมตั้งค่าตะกร้าผูก ระบบจะส่ง Error 400 (Bad Request) ทันทีเพื่อปฏิเสธการดึงคืน ป้องกันปัญหารายชื่อลูกค้า "ค้างเติ่ง" (Stranded Records) หรือข้อมูลสูญหาย (Zero Fallback Policy)
- **Database-Level SQL Optimization:** เงื่อนไขการคัดกรองจะถูกส่งไปประมวลผลที่ Database โดยตรง (ผ่าน `EXISTS` และ `NOT EXISTS`) ทำให้รองรับลูกค้าระดับแสนรายการได้โดยไม่เกิดปัญหา Memory Out
- **Smart Cap (กันดึงเกิน):** พิมพ์ลิมิตจำนวนคนที่จะดึงได้ ระบบจะตรวจจับและดึง/โอนให้สูงสุดเท่าที่มีจริง ไม่เกิด Error

## 🔄 5. การรีเซ็ตรอบ (Manual Reset)

เมื่อต้องการวนลูกค้ารอบใหม่ให้พนักงานคนเดิม (เริ่ม Life Cycle ใหม่):
1. เข้าเมนู **"Manual Reset"** (มุมขวาบน)
2. เลือกรอบที่ต้องการ หรือค้นหาตามเบอร์โทร/รายชื่อ Agent
3. กดยืนยันเพื่อล้างตาราง `customer_assign_check` สำหรับลูกค้ารายนั้นๆ
4. ผลลัพธ์: พนักงานคนเดิมจะได้รับลูกค้ารายนี้อีกครั้งโดยไม่ติดตัวกรอง Smart Allocation

---

## 🚫 6. การปลดบล็อคลูกค้า (Unblock Target)

ลูกค้าในตะกร้า **"ลูกค้าบล็อค"** ไม่สามารถกดแจกตรงๆ ได้ ต้องผ่านกระบวนการปลดบล็อค:
1. กดการ์ด 🚫 ลูกค้าบล็อค
2. เลือกรายชื่อที่ต้องการให้โอกาส
3. เลือกปลายทาง (เช่น ถัง 6-12 เดือน)
4. กด **"✅ ปลดบล็อค"** → สถานะบล็อคจะถูกล้างและกลับเข้าสู่ Flow แจกงานปกติ

## 📊 7. ระบบประวัติการแจกงานและดึงคืน (Distribution & Reclaim Report)

หลังจากการแจกงานเสร็จสิ้น ระบบจะทำการ **Snapshot** ข้อมูลการแจกงานรอบนั้นๆ เอาไว้โดยอัตโนมัติ เพื่อให้หัวหน้างานสามารถตรวจสอบย้อนหลังและนำออกข้อมูลได้:

### 📂 การทำงานของ Database (Session Logging)
- **`distribution_sessions`**: เก็บข้อมูลภาพรวมของการแจก 1 ครั้ง (ใครเป็นคนแจก, โหมดอะไร, แจกไปกี่คน, และ `agent_snapshot` สรุปยอดแจกรายบุคคล)
- **`distribution_session_details`**: เก็บความสัมพันธ์แบบ 1-to-Many ว่าพนักงานคนไหน ได้รับลูกค้าเบอร์อะไรบ้าง
- ⚡ **Lazy Loading (On-Demand Fetching):** ในหน้า UI จะโหลดเฉพาะตาราง `sessions` และ `agent_snapshot` มาก่อน เพื่อประหยัด Memory ของเบราว์เซอร์สูงสุด และจะดึงตาราง `details` ก็ต่อเมื่อผู้ใช้กด "ดูรายละเอียด" หรือ "Export Excel" เท่านั้น (ป้องกันจอค้างเมื่อมีรายการนับหมื่น)

### 🖥️ การแสดงผลหน้าจอประวัติ (Report UI Enhancements)
- **Grid Filter Layout:** ตัวกรองถูกจัดระเบียบแบบ Grid 5 คอลัมน์ รองรับการกรองละเอียด:
  1. วันที่เริ่มต้น
  2. วันที่สิ้นสุด
  3. ประเภท (แจก / ดึงคืน)
  4. ตะกร้าต้นทาง (Basket)
  5. Session Tag
- **ระบบป้ายสี (Color Badges):** 
  - 🔵 หากเป็นรายการแจกงาน (Distribution) จะแสดงป้ายสีฟ้าพร้อมคำว่า **"แจก (...)"**
  - 🔴 หากเป็นรายการดึงคืนหรือโอนย้าย (Reclaim/Transfer) จะแสดงป้ายสีแดงพร้อมคำว่า **"ดึงคืน (...)"** ให้สังเกตง่าย

### 🏷️ ระบบจัดการ Session Tag (Centralized Taxonomy & Normalization)
ระบบแจกงาน V2 ได้รับการรีแฟคเตอร์ (Refactor) โครงสร้างการเก็บข้อมูล Tag ใหม่ทั้งหมด เพื่อแก้ปัญหาข้อมูลขยะ (Typo/Duplication) โดยยึดหลัก **Database Normalization (Best Practice)**:
- **Centralized Database Table:** ยกเลิกการเก็บชื่อ Tag เป็นตัวอักษรดิบๆ ในประวัติการแจกงาน และเปลี่ยนมาสร้างตารางกลาง `distribution_tags` เพื่อเก็บ Master Data แทน (เก็บชื่อ Tag และรหัสสี)
- **Foreign Key Integration:** ในตารางประวัติการแจกงาน (`distribution_sessions`) จะเก็บเพียงรหัส `tag_id` (ตัวเลข) เท่านั้น ส่งผลให้:
  - 🛡️ **Data Integrity:** ข้อมูลไม่ผิดเพี้ยน พิมพ์ผิดไม่ได้อีกต่อไป
  - 🔄 **Cascading Updates:** หากแอดมินแก้ไขชื่อ Tag จาก "ล็อตเช้า" เป็น "ล็อตเช้า (ด่วน)" ประวัติแจกงานเก่าๆ นับหมื่นรายการจะแสดงผลเป็นชื่อใหม่ทันที โดยไม่ต้องรันสคริปต์ตามแก้ Data
- **Tag Management Modal:** สร้างหน้าต่างจัดการ Tag ส่วนกลางที่แยกตัวออกมา (Stand-alone Modal) ให้แอดมินสามารถเพิ่ม ลบ แก้ไขชื่อ และกำหนดสี (Color Palette) ประจำ Tag ได้อย่างสวยงาม
- **Smart Select UI (`SessionTagSelect`):** เปลี่ยนจากกล่องพิมพ์ข้อความ มาเป็น Dropdown Component ทันสมัยที่ดึงรายชื่อ Tag จากฐานข้อมูลมาแสดงผลพร้อมแถบสี (Color Badge) ทำให้ UX การใช้งานชัดเจนและเป็นระเบียบ

### 📥 การนำออกไฟล์ Excel (Best Practice Export)
การกดปุ่มส่งออก จะใช้ตัวกรองบนหน้าจอเสมอ (WYSIWYG - What You See Is What You Get):
1. **Summary Snapshot**: หน้าสรุปตารางการแจกงาน 
   - รองรับการนับ **"จำนวนพนักงาน (Agents)"** ที่ได้รับงานในรอบนั้นๆ
2. **Customer Details**: ตารางรายชื่อลูกค้าแบบละเอียด (รหัส, ชื่อ, เบอร์โทร) แตกแจกแจงตามพนักงานที่ได้รับ เหมาะสำหรับนำไปกระทบยอดหรือตรวจสอบย้อนหลัง

## ↩️ 8. ระบบดึงรายชื่อกลับคืน (Undo Distribution / Reroll System)

หากหัวหน้างานทำการแจกงานผิดพลาด สามารถทำการดึงรายชื่อลูกค้าที่แจกไปแล้วกลับเข้าถังเดิมได้ทันที:

- **Safe Mode (แนะนำ):** ดึงกลับเฉพาะลูกค้าที่พนักงานยัง **ไม่ได้แตะต้อง (ไม่ได้อัปเดตข้อมูล)** ภายในเวลา 10 วินาทีหลังการแจกงาน หากลูกค้าคนไหนถูกโทรและเปลี่ยนสถานะไปแล้ว ระบบจะปล่อยผ่าน (Skip) ทันทีเพื่อความปลอดภัยของข้อมูล
- **Force Mode (ฉุกเฉิน):** ดึงลูกค้าทุกคนในล็อตแจกงานนั้นกลับคืน **100%** โดยไม่สนว่าพนักงานจะเริ่มโทรแล้วหรือไม่ ใช้ในกรณีที่มีการตั้งค่าเป้าหมายผิดพลาดร้ายแรง

**กระบวนการหลังบ้านตอนกด Undo:**
1. อัปเดตตาราง `customers` (ดึง `assigned_to`, `current_basket_key`, `lifecycle_status` กลับไปเป็นค่าเดิมก่อนแจก)
2. ลบประวัติการรับงานรอบนี้ใน `customer_assign_check` ออก เพื่อให้พนักงานคนเดิมมีสิทธิ์ได้รับรายชื่อนี้ใหม่ในอนาคต (ล้างคราบว่าเคยรับในรอบที่แล้ว)
3. เขียน Log ลงในตาราง `basket_transition_log` โดยระบุ `transition_type = 'reclaim'` และหมายเหตุว่าเป็นการ Undo

## 🧹 9. ระบบบริหารจัดการประวัติแจกงาน (Data Cleanup System)

เพื่อไม่ให้ตาราง `distribution_session_details` ที่บันทึกรายชื่อ 1-to-Many บวมจนเกินไป (ทำให้เกิดปัญหา Database Performance):

- ระบบมีปุ่ม **"🧹 เคลียร์ประวัติเก่า"** สำหรับ Admin (`is_system = 1`)
- **Retention Policy:** สามารถเลือกอายุของข้อมูลที่ต้องการลบ (1, 3, 6, 12 เดือน) ระบบจะลบเฉพาะตาราง `details` ทิ้ง แต่ยังคงตาราง `sessions` ไว้เพื่อให้ยอดสรุปคงเดิม
- **RBAC Enforcement:**
  - `is_system = 1` ธรรมดา จะลบได้เฉพาะบริษัทของตัวเอง
  - `is_system = 1` + `role = 'super_admin'` จะสามารถเลือกลบข้อมูลแบบเหมาทุกบริษัท (All Companies) ได้ในคลิกเดียว

## ⏱️ 12. รายงานสรุปความเคลื่อนไหวจากระบบอัตโนมัติ (Cron Log Viewer)

### 🏗️ โครงสร้างการทำงาน (Architecture & Flow)
1. **API Endpoint (`api/DistributionV2/get_cron_logs.php`):**
   - ดึงประวัติจากตาราง `cron_execution_logs` เฉพาะรอบที่ทำงานสำเร็จ (status = 'success')

   - มีระบบความปลอดภัย (Filter) ป้องกันไม่ให้ผู้ใช้เห็นข้อมูลข้ามบริษัทหากไม่มีสิทธิ์

   - มีการคำนวณส่วนต่าง (Diff Calculation) เพื่อสรุปยอดลูกค้าที่ถูก "ย้ายลงตะกร้ากลาง" (Distribution Pool) อย่างชัดเจน

3. **ความปลอดภัย (Security Focus):**

## 🛡️ 13. การรับรองมาตรฐานระบบ (Best Practice Assurance)

ระบบ Distribution V2 ได้ผ่านการตรวจสอบโค้ดและปรับปรุงโครงสร้างให้สอดคล้องกับมาตรฐาน (Best Practices) ระดับ Enterprise-grade เรียบร้อยแล้วในด้านต่างๆ ดังนี้:

- **Bulk SQL Operations (High-Performance Processing):** โครงสร้างโค้ดส่วนการทำ Distribute, Reclaim และ Undo ทั้งหมด ถูกเปลี่ยนจากการวนลูปทีละแถว (Loop-based) มาเป็น Bulk SQL (Bulk `INSERT`, Bulk `UPDATE ... CASE WHEN ...`) ซึ่งสามารถเขียน/แก้ไขข้อมูลลูกค้าทีละ 500-1000 รายการในการรัน Query เพียงครั้งเดียว ช่วยให้ประมวลผลข้อมูลนับหมื่นรายการได้ในระดับมิลลิวินาที (Milliseconds)
- **Lazy Loading Data Architecture:** หน้าจอ UI จะไม่ดึง Payload มหาศาลมาทิ้งไว้ล่วงหน้า แต่จะโหลดเฉพาะข้อมูลสรุปย่อย และดึงข้อมูลดิบ (Raw Data) เฉพาะเมื่อมีการกดกางแถว (Expand) หรือกดส่งออก Excel (Export) ลดภาระ Memory และยืดอายุการทำงานแบบเสถียร
- **Robust Database Queries:** ใช้ `EXISTS`/`NOT EXISTS` แทนการทำ Sub-query ดึงลิสต์ หรือ In-clause ขนาดใหญ่ ช่วยประหยัด RAM และป้องกันปัญหาคอขวด 
- **ACID Transactions:** ทุกคำสั่งที่เปลี่ยนสถานะหรือข้อมูลลูกค้าจะถูกหุ้มด้วย Database Transaction เสมอ ทำให้ถ้าเกิด Error ระหว่างทาง ข้อมูลทั้งหมดจะ Rollback กลับ ป้องกันข้อมูลพังครึ่งทาง

## 📈 14. การส่งออกสถิติการทำงานแบบ MECE (Session Performance Export)

เพื่อประเมินผลการโทรของรายชื่อแจกงานแต่ละรอบ (Session) ได้อย่างแม่นยำ ระบบได้เพิ่ม **โหมดส่งออกรูปแบบที่ 8: สถิติการโทรรายบุคคล (Call Stats)** ที่รองรับ **Mutually Exclusive (MECE) Logic** อย่างเต็มรูปแบบ

### หลักการทำงาน
- **Pivot Table Layout:** ข้อมูลถูกจัดรูปแบบให้คล้าย Pivot Table ใน Excel ทำให้เห็นยอดสรุปแยกตามพนักงานแต่ละคน และแบ่งช่วงคอลัมน์ออกตามกลุ่มตะกร้าเป้าหมาย (เช่น `[ลูกค้าใหม่]`, `[ด่วนตัว 1-2 เดือน]`) ได้ชัดเจน
- **กรองผลลัพธ์แบบ Time-Bound:** ระบบจะนับผลการโทรและการนัดหมาย **เฉพาะที่เกิดขึ้นหลังจากลูกค้าถูกแจกงานในรอบนั้นๆ เท่านั้น** (โดยการเช็ค `created_at` ของ Session) ช่วยให้ผลงานของพนักงานสะท้อนความเป็นจริงมากที่สุด ป้องกันการเหมาผลงานจากอดีต
- **MECE Categories:** ผลการโทรจะถูกแบ่งออกเป็น 4 หมวดที่ไม่ทับซ้อนกัน ได้แก่:
  1. `ในมือ` (ยอดรวมลูกค้าที่ได้รับ)
  2. `ยังไม่โทร` (ไม่เคยมีการกดโทรหลังจากรับงาน)
  3. `โทรแล้วไม่นัดหมาย` (มีการโทร แต่ไม่มีบันทึกนัดหมาย)
  4. `โทรแล้วนัดหมาย` (มีการโทรและมีการนัดหมาย)
  5. `นัดหมายแล้วไม่มีโทร` (มีการนัดหมาย แต่ไม่มีประวัติการกดโทร - เคสนี้เกิดขึ้นได้ยาก แต่นำมาเช็คความสมบูรณ์ของระบบ)
- **Grand Total (รวมทุกตะกร้า):** มีคอลัมน์กรุ๊ปสุดท้ายที่แสดงผลรวมยอดของทุกตะกร้าในรอบแจกนั้น เพื่อให้ผู้จัดการสามารถดูภาพรวมผลงานของแต่ละพนักงานได้อย่างรวดเร็ว
- **Undo Exclusion:** ตัดข้อมูล Session ที่ถูก Undo (ดึงคืนทั้งหมด) ออกจากการสรุปผลอัตโนมัติ ដើម្បីความแม่นยำของ Data Analysis
- **Fail-Safe Integrity:** ยกเลิกระบบ "เดาใจ (Fallback)" เช่น หากแอดมินไม่ได้ตั้งค่าตะกร้าเป้าหมายตอนดึงคืน ระบบจะปฏิเสธการทำรายการทันที (Reject) เพื่อรักษาความถูกต้องของข้อมูล (Zero Tolerance for Data Corruption)
- **Component Modularity:** แยกไฟล์ React ให้เป็น Component เล็กๆ ที่ทำหน้าที่เฉพาะทางเดียว (Single Responsibility Principle) ช่วยให้โค้ดดูแลรักษาง่าย และลดภาระการ Re-render ของเบราว์เซอร์
